# Issue-Driven Development y GitHub Flow

La especificación y las tareas de Spec Kit definen el alcance. GitHub Issues registra la ejecución. [El orden y la matriz](../specs/001-codificacion-web/tasks.md) conectan ambos. La preparación actual es local. Publicar, crear issues o iniciar T001 requiere aprobación explícita. Configurar reglas del remoto requiere autorización administrativa.

## Etapas y condiciones de avance

| Etapa        | Acción de Codex                                                                                                                                                                                                                                           | Condición para continuar                                                                                                                                    |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Spec Kit     | Revisar Specify, Clarify, Plan y Tasks. Para un cambio de alcance, actualizar los artefactos antes de programar                                                                                                                                           | Tarea con resultado pequeño, FR y CA aplicables, casos Q y dependencias explícitas                                                                          |
| GitHub Issue | Buscar primero un issue por ID T. Crear uno por tarea con la plantilla, vincular las dependencias por número y asignar milestone, prioridad, tipo y área. Registrar el número real en la matriz                                                           | Issue completo y aprobado. Las dependencias pueden estar abiertas al cargar el backlog, pero deben estar integradas antes de iniciar la rama                |
| Branch       | Partir de `origin/main` actualizado en una rama independiente `codex/issue-<n>-<resumen>`. Mantener un solo issue por rama y cambios pequeños                                                                                                             | Base y dependencias verificadas. Rama vinculada al issue en GitHub cuando esté disponible                                                                   |
| TDD          | Aplicar `codificaweb-tdd`. Escribir prueba, observar el fallo esperado, implementar lo mínimo y refactorizar con la prueba en verde. Para infraestructura, guardar la evidencia de su validación                                                          | Criterios cubiertos y pruebas locales relevantes ejecutadas. Commits pequeños con `Refs #<n>` y el ID T. Registrar archivos y resultados Red–Green–Refactor |
| Pull Request | Abrir un PR a `main` con `Closes #<n>` en el cuerpo. Incluir IDs, archivos de prueba, resultados, alcance y riesgos. Usar borrador si está en curso                                                                                                       | PR enlazado y revisable. Las dependencias ya figuran en `main`                                                                                              |
| CI           | Revisar GitHub Actions sobre la última revisión del PR. Si falla, corregir en la misma rama y esperar una nueva ejecución                                                                                                                                 | Todos los checks requeridos terminan correctamente. Un check fallido, pendiente, cancelado o ausente bloquea la integración                                 |
| Review       | Pedir revisión independiente. Revisar el diff, criterios, pruebas, permisos y trazabilidad. Resolver conversaciones. Tras cambios, obtener revisión y CI sobre la nueva revisión                                                                          | Aprobación independiente cuando se pueda exigir. Sin revisor disponible, presentar el PR al usuario y esperar su decisión explícita                         |
| Merge        | Integrar mediante PR, preferentemente squash. Conservar `Refs #<n>` e ID T en el commit final. Verificar cierre automático del issue, SHA en `main` y resultado de CI posterior. Registrar el PR en la matriz y eliminar la rama del issue según política | Issue cerrado por integración, PR y SHA consultables y dependencias desbloqueadas. Si CI en `main` falla, abrir seguimiento y detener tareas dependientes   |

La traza mínima es `FR/CA → T → issue → rama → archivos Q → commits → PR → ejecución CI → SHA de main`. Añadir en el PR de cada tarea el issue y las rutas de prueba a la matriz. Cuando exista el número de PR, completar el enlace en esa misma rama antes de la revisión final. El PR enlaza a su issue y muestra el commit resultante tras integrar. Si el cierre automático falla, verificar primero el merge en la rama predeterminada y registrar allí el enlace antes de cerrar el issue. [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow) · [Vincular un PR con un issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

## Milestones y etiquetas propuestas

| Milestone                        | Tareas    | Resultado                                          |
| -------------------------------- | --------- | -------------------------------------------------- |
| M0 · Preparación del repositorio | T000      | Plan y workflow base integrados mediante PR        |
| M1 · Selección y resaltado       | T001–T004 | Seleccionar, asignar y pintar en la extensión real |
| M2 · Persistencia                | T005–T006 | Recuperar evidencia                                |
| M3 · Organización y búsqueda     | T008–T011 | Proyectos, códigos, filtros y navegación           |
| M4 · Intercambio y validación    | T012–T013 | JSON y validación de versión                       |

Asignar un tipo entre `type:feature`, `type:infra` y `type:bug`, un área principal entre `area:extension`, `area:anchor`, `area:data`, `area:panel` y `area:quality`, y una prioridad. `priority:p0` desbloquea el arranque, protege integridad o resuelve bloqueos de versión. `priority:p1` identifica el resto del alcance comprometido. `priority:p2` identifica trabajo posterior. La prioridad solo ordena issues con dependencias satisfechas. Usar dependencias nativas cuando estén disponibles y referencias `#<n>` en la descripción como registro verificable.

## CI y protección de main

[El workflow local](../.github/workflows/ci.yml) corre en PRs a `main` y en pushes a `main`. El check estable se llama **CI / Verificación**. Usa Node de `.node-version`, Corepack fijado y pnpm de `packageManager` con lockfile congelado. Ejecuta formato, lint y tipos en ambas etapas. En planificación, un guard impide incorporar `src/` o `tests/` con las comprobaciones de producto desactivadas. T001 activa la etapa de producto y debe pasar pruebas Vitest, cobertura, compilación y E2E Chromium desde su propio PR. Conservar el nombre del check. La validación manual de Chrome y Brave sigue siendo requisito de versión. [GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) · [Playwright para extensiones](https://playwright.dev/docs/chrome-extensions)

Tras aprobación, verificar que `main` sea la rama predeterminada y que Issues y Actions estén habilitados. En T000, comprobar que el check aparece en el PR. Cuando el repositorio, el plan y los permisos lo permitan, solicitar un ruleset o protección de `main` que exija PR, al menos una aprobación ajena al autor, revisión vigente tras cambios, conversaciones resueltas y el check de Actions correcto sobre una base actualizada. Bloquear pushes directos, force pushes y borrado de `main`. Si GitHub todavía no permite seleccionar el check nuevo, el mantenedor debe revisar el resultado de T000 antes de integrarlo y activar el requisito tan pronto esté disponible, antes de T001. Si falta protección automática, aplicar los mismos controles como política de merge y dejar constancia en el PR. [Rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)

## Herramientas para Codex

Se comprobó que `gh` 2.95.0 está instalado y que `origin` apunta al repositorio previsto. Tras aprobación, validar identidad y acceso con `gh auth status` y comprobar repo y rama predeterminada con `gh repo view`. Preferir `gh` junto con Git local para buscar issues, abrir PRs y consultar checks de forma reproducible. Pasar cuerpos multilínea con `--body-file`. El conector GitHub de Codex está disponible para instalar y puede servir para inspección y triaje. Se mantiene sin instalar durante esta etapa. Las mismas autorizaciones se aplican a cualquier herramienta elegida. [GitHub CLI para issues](https://cli.github.com/manual/gh_issue) · [GitHub CLI para PRs](https://cli.github.com/manual/gh_pr)
